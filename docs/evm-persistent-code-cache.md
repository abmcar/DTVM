# EVM 持久化编译缓存 — 使用说明

把 JIT 编译产物(ELF object)落盘复用,避免每次进程重启都重新编译合约。
**默认关闭,纯 opt-in**;不开时行为与合入前完全一致。

分支:`feat/evm-persistent-code-cache`(基于 `338d123`,4 个 commit)
无需任何 CMake 开关(位于已启用的 `ZEN_ENABLE_MULTIPASS_JIT` 内)。

---

## 1. 怎么开

两个 EVMC 选项(`evmc_set_option`):

| 选项 | 取值 | 说明 |
|---|---|---|
| `code_cache_dir` | 路径 | 缓存目录,需可写。不设=不启用 |
| `code_cache_mode` | `off` / `ro` / `rw` | 默认 `off` |

模式语义(`src/vm/dt_evmc_vm.cpp:394`,`src/runtime/config.h:61`):

- **`rw`(=2)读 + 写。日常用这个。** 命中就用,没有就编译并写入,自动积累。
- `ro`(=1)只读,从不写。用于测量——排除写回抖动。日常用它等于放弃积累。
- `off`(=0)默认。完全不启用。

经由 reth 适配器时(需 `abmcar/reth` 分支 `evmc-backend-and-replay-docs`
提交 `b778d43f7` 及之后——该提交加入了透传;逗号分隔的 name=value 走
与固定选项相同的受检 `set_option` 路径,非法条目启动即失败):

```
RETH_SUBJECT_EVMC_OPTIONS="code_cache_dir=/path/to/cache,code_cache_mode=rw"
```

## 2. 能快多少(实测,主网 25778671..25779670)

对照:同一区间、同一二进制、无缓存基线 **37.895 s/块**。

| 场景 | s/块 | 收益 |
|---|---|---|
| 无缓存(基线) | 37.895 | — |
| **`rw` 首次跑(缓存从空开始建)** | **16.809** | **2.25×** |
| **`ro` 缓存已建好(正式值)** | **1.795** | **21.1×(下界,见 §7)** |

**关键点:收益不需要"先付一次再享受"。** 首次跑本身就是 2.25×,因为趟内早先
编过的合约后面就命中了。逐段衰减:

| 区段 | s/块 |
|---|---|
| Q1(前 ~120 块) | 41.44 |
| Q2 | 23.46 |
| Q3 | 16.06 |
| Q4 | 13.22 |
| 趟尾边际(仍含写回与新合约编译) | ~8.5 |

注意:~8.5 是 **rw 趟内的边际成本**,不是缓存全热的稳态——稳态见上表
`ro` 正式值 1.795。早期 20 块 shakedown 报过 8.59 s/块,那是冷 VM、
装载密集态的高估,**已被 1.795 取代,不要再引用**。

短区间同样净赚(前 20 块:126.44 → 106.21,1.19×),**区间越长收益越大**。

**编译地板**:实测 ≈**1.0 秒/新合约**(两条独立路径交叉验证:1.15 与 0.98)。
缓存消除"再次见到"的编译,消不掉"首次见到"。所以首建成本下界 ≈ 唯一合约数 × 1 秒。

## 3. ⚠ 三条硬约束(决定缓存能否搬运)

缓存 key = SHA256(buildTag ‖ targetFeatures ‖ Revision ‖ Flags ‖ MemoryStride ‖ len ‖ bytecode)

1. **`buildTag()` 含 `__DATE__ " " __TIME__`(编译时间戳)。**
   ⇒ **库重编一次(哪怕源码一字未改),整份缓存立即全部失效。**
   ⇒ 缓存只能连**产生它的那个具体 `.so` 二进制**一起搬,不能跨独立构建迁移。
   *(这是 Phase 3 换成源码 hash 之前的保守方案。)*
2. **`getTargetFeatureString()` = 宿主 CPU 特征。** 跨机要求 CPU 特征集一致。
3. **RA 设置在 key 里**(Flags bit1 = `DisableGreedyRA`)。
   greedy 建的缓存对 FastRA 运行者**零命中**。⇒ 必须先定 RA,再定二进制,再建缓存。

**推论:与其搬运缓存文件,不如让每个人本地自己建。**
因为建库趟本身已经是 2.25×,本地建几乎是免费的。

## 4. 磁盘占用

约 **394 KB / 模块**。实测 1000 块 = 13,811 条 ≈ **4.5 GB**。

外推请谨慎:Heaps 律拟合 `U(n)=452.11·n^0.5136` 在 n=1000 处**高估约 14%**
(预测 15,710,实测 13,811),大 n 处偏乐观。

---

## 5. 已知限制

- **L1 内存 LRU 上限仍是 4096**(`dt_evmc_vm.cpp:248`),磁盘缓存**没有**解除它。
  未命中的后果从"重编译"变成"读盘+重装载",天花板本身没动。
- 长跑中唯一合约数远超 4096,但因合约访问是重尾分布,实际访问未命中率远低于
  "唯一合约未命中率"——**不要用 `U(n)/4096` 估算未命中率,那假设了均匀访问。**
- 若做引擎对比 benchmark,缓存会改变被测对象:所有臂要么统一 `off`,要么统一开启并在报告中写明。

## 6. 验收结果(1000 块主网,25778671..25779670)

| 臂 | rc | errs | s/块 | 说明 |
|---|---|---|---|---|
| `rw` | 0 | 0 | 16.809 | 4.57h 建出 13,811 条(5.4 GB) |
| `ro` | 0 | 0 | **1.795** | 执行段墙钟 29.8 分钟;缓存零新增 = 全命中 |

两臂共识门全过。引擎对照(同区间,s/块):stock reth 0.0514、
evmone 0.1200、DTVM 无缓存 37.895(737.8× vs stock)、
**DTVM+缓存 1.795(34.9× vs stock)**。

## 7. 引用这些数字前必读的四条

1. **稳态值是 1.795,不是 8.59。** 8.59 来自早期 20 块 shakedown(冷 VM、
   装载密集),由它推出的任何倍数(如 12.4×)一律作废重算。
2. **29.8 分钟只是执行阶段。** ro 用全新克隆的 datadir,开库冷一致性
   检查另花 1h07m49s。排期按"DB 准备 + 执行"两段算。
3. **perf 的 `llvm::SHA256::hashBlock 32.5%` 是 on-CPU 占比,不是墙钟占比。**
   on-CPU 只占墙钟 13%,SHA256 实际 ≈ 墙钟 4.2%(0.076 s/块)。ro 残余的
   主体是 **off-CPU 的冷 mdbx 状态读(≈87%,1.562 s/块)**——那是 DB 侧
   成本,暖 datadir 下消失,与缓存机制无关。
4. **21.1× 是下界。** 基线 37.895 测于暖 datadir,ro 含冷读罚;
   冷 mdbx 控制臂量化后该倍数只会上修。

另:rw 趟尾边际(~8.5)与 ro(1.795)之差里约 0.9 s/块是**写回代价**
(每新合约 SHA256 + 写 394 KB),只在建库趟存在。

## 8. 复现(witness 回放)

复现一律走 **witness 回放** —— 状态随块一起带来,不需要一份同步好的数据库。
同一份缓存在这个场景下另测了一组三臂(10 块主网 25625046–25625055,
每块一个独立进程,30/30 rc=0 且 pre/postStateRoot 全部验证通过):

| 臂 | s/块 | 相对 `nocache` |
|---|---|---|
| `nocache` | 492.34 | 1× |
| `rw`(建库) | 206.87 | 2.4× |
| **`ro`(全命中)** | **3.006** | **163.8×** |

两条限定,不带上会误读:

- **163.8× 与 §6 的 21.1× 不可互引。** 每块一个独立进程时装载成本每块重付,
  这是磁盘缓存的最佳展示场景、却是引擎的最坏场景。`ro` 的 3.006 s 里纯执行
  只有 95 ms,其余 97% 是装载,长驻进程不会有。
- **492 s 只在"每块一个独立进程"下成立。** 它和 §2 的无缓存值 37.895 s/块**不能相除** ——
  两个数的分子是不同的工作量:witness 每块从零编译该块触及的**全部**合约;
  长驻进程只编译**新出现**的合约,外加 L1(4096 条,见 §5)容量不足导致的
  驱逐重编译。窗口长度、进程模型、是否读数据库也都不同。
  封存分片数据能看到这个差别怎么拉开:同一进程内首块 340–520 s,
  17 块之内降到 50–150 s。

**每块的合约数不必从计时反推。** bundle 自带 `witness.codes`(该块触及的去重
字节码集合,与计时数据无关):10 块均值 **307.9**,跨度 213–527,并集 1391。
对它做最小二乘(n=10):

| 臂 | 自变量 | 边际 | 截距 | R² |
|---|---|---:|---:|---:|
| `nocache` | 合约数 | 1.445 s/合约 | 47.3 s | 0.969 |
| `nocache` | **字节码 MB** | **154.8 s/MB** | 21.1 s | **0.987** |
| `ro` | 合约数 | 9.0 ms/合约 | 0.22 s | 0.966 |
| `ro` | **字节码 MB** | **0.97 s/MB** | 0.05 s | **0.989** |

**编译和装载都由字节码总量驱动,不是合约个数** —— 两臂按体积回归都拟合更好、
截距更小。交叉核对(不构成恒等变换):总时间比 492.34/3.006 = **163.8**,
两条独立回归的斜率比 1.445/0.0090 = **159.9**,差 2.4%,说明两臂截距成分都小。

**rw 臂给出了缓存机制最直接的一句话。** 按块自身规模回归 `rw` 拟合很差
(R²=0.31,斜率统计上不显著,t=1.90),但那是自变量选错了 —— `rw` 的耗时由
该块有多少字节码**此前没出现过**决定,而这个量语料就能算(按运行顺序取差集):

| 臂 | 自变量 | 斜率 | 截距 | R² | t |
|---|---|---:|---:|---:|---:|
| `rw` | 块自身字节码 MB | 87.7 s/MB | −60.1 s | 0.304 | 1.87 |
| `rw` | **新增**字节码 MB | **150.5 s/MB** | +8.0 s | **0.998** | 57.7 |
| `nocache` | 块自身字节码 MB | 154.8 s/MB | +21.1 s | 0.987 | 24.6 |

`rw` 对新增字节码的编译单价 150.5 s/MB,与 `nocache` 在**另一条臂上独立测得**的
154.8 s/MB 相差 **2.8%**。**缓存没有让编译变快,它让编译不再发生** —— 付费的
字节码从"该块全部"变成"此前没见过的",单价一分没动。新增合约数从首块 252 降到
末块 41,缓存填充过程逐块可见。

**缓存长到 9.6 倍,装载成本没有变化。** 把缓存从 1,460 条(595 MB)扩到
14,051 条(5.5 GB),对同样这 10 块再跑一次 `ro` —— 同语料、同二进制、同边界,
唯一变量是规模。两臂各跑两遍取第二遍,使页缓存状态一致:

| 缓存规模 | s/块 | ms/合约 | s/MB | R² |
|---|---:|---:|---:|---:|
| 1,460 条 / 595 MB | 3.0107 | 9.12 | 0.980 | 0.988 |
| 14,051 条 / 5.5 GB | 3.0101 | 9.01 | 0.967 | 0.990 |
| **配对差(9.62×)** | **−0.0006** | SD 0.0198 | t = −0.09 | df=9,临界 2.262 |

两臂各自 20/20 通过 `postStateRoot` 验证,且**同一块在两臂算出的状态根逐块
相同(10/10)**,连同早先那次独立的 `ro` 运行三方一致 —— 这排除了速度检验
看不见的失效模式:**大缓存里若有 key 碰撞或损坏条目、装载出错误的代码,
表现是状态根分叉而不是变慢。**

**最小可检测效应 0.0142 s = 整块的 0.47%**,即 9.62×
规模下每次装载惩罚 **< 0.05 ms**。查找走 ext4 htree,1.4k→14k 只多一两层树深。

两条限制:

- **外推边界**:5.5 GB 全驻留页缓存(机器 123 GB RAM)。10 万合约约 40 GB,
  超出页缓存后是真盘读,本实验推不到那里。
- **口径**:同一实验的未受控首版用 wall 口径,显示大缓存"快 1.6%",方向还与
  规模惩罚相反 —— 那 1.6% 全是进程启动与 JSON 解析噪声。**这类小效应必须用
  phase 口径**,wall 的噪声底比效应本身还大。

需要两个仓库:

- **DTVM(带缓存)**:本仓库分支 `feat/evm-persistent-code-cache`
- **回放器**:<https://github.com/abmcar/reth> 分支 `evmc-backend-and-replay-docs`
  —— 用法见其 `docs/witness-replay.md`;缓存 option 经环境变量
  `RETH_SUBJECT_EVMC_OPTIONS` 透传给 EVMC 后端

逐步命令(建 DTVM、建回放器、备语料、先 `rw` 后 `ro`)见验收报告 §6。
