\section{Introduction}

The execution layer of a blockchain information system is a replicated
consensus state machine: every node on the consensus path must produce
bit-identical results for the same transaction. The EVM is a widely
deployed smart-contract execution environment; when a client enables a
JIT, the compiler becomes part of the consensus-critical path.
Peephole rewrites in the JIT act directly at machine-code generation,
so their correctness bears directly on the determinism of on-chain
execution; a wrong equivalence judgment, deployed on only some
clients, may trigger a chain fork.

Existing formal verification of EVM peephole rewrites mostly targets
the bytecode block-level abstraction. The machine-level patterns
emitted by a JIT during code generation---especially the multi-word
carry chains that arise when the 256-bit word length is lowered onto
64-bit hardware---sit at a different abstraction layer from bytecode
rules and are awkward to validate as single stock LLVM/Alive2 peephole
queries. The root cause is how IRs model bit-level side-products. In
LLVM IR, basic arithmetic is defined only on $N$-bit
integers; the carry bit must be retrieved through an intrinsic that
returns a multi-return tuple of \{result, carry\}. Rules depending on
this side-product can be expressed only through indirect structures in
Alive~\cite{alive} and similar tools; the bottleneck is the IR's
expressiveness, not the SMT solver~\cite{demoura2008z3}. For a
consensus-critical JIT, an unchecked rule class leaves the engineer
with three choices---drop it (performance), ship it without verification
(safety), or hand-prove it (scalability).

Our approach: extend the IR with first-class bit-vector operators so
that SMT-checkable peephole rules cover a larger surface, without
modifying the solver or relaxing the differential-test threshold. In
dMIR, the bit-level patterns that previously required indirect
multi-return encoding become first-class operators, so the
corresponding rules fall within Z3 bit-vector equivalence. The SMT scope
is dMIR arithmetic/flag semantics; gas, memory, storage, and x86
equivalence remain outside it.

\paragraph{Contributions.}
\begin{enumerate}
  \item \textbf{A dMIR extension for SMT-checkable carry-chain
    peepholes.} First-class carry operators make the four cases in
    Table~\ref{tab:cannot-express} single Z3 bit-vector queries rather
    than indirect LLVM/Alive2 tuple encodings. The two-tier rule set has
    \textbf{70} dMIR rules (SMT-checked for arithmetic/flags) and
    \textbf{13} x86 rules (differentially tested; no separate SMT check).
  \item \textbf{An enumerable, Z3-admitted search space covering the
    production dMIR set.} A capacity run evaluates \textbf{853} candidates
    (\textbf{98.7\%} algebraic, \textbf{21.8\%} carry admitted by Z3); a
    separate coverage run admits \textbf{1966} rules whose canonical LHSs
    cover all \textbf{70/70} hand-designed production rules. This is
    post-hoc reachability, not blind recall (\S\ref{sec:coverage-scope}).
  \item \textbf{End-to-end performance and correctness.} Across the
    \textbf{27} EVM benchmarks of evmone-bench, the geometric-mean
    speedup is \textbf{+7.24\%} (95\% confidence interval
    [+2.59\%, +12.11\%], which excludes zero),
    with a peak of \textbf{+25.79\%}; \textbf{5884} differential tests
    report byte-identical final state and identical gas accounting in a
    same-engine DTVM self-A/B comparison.
\end{enumerate}

Relative to the EVM bytecode block-level formal rule set of
Albert et al.~\cite{verified_evm_cav23} at CAV 2023, the rule set in this
paper operates at the JIT intermediate representation and machine-code
layers that the bytecode abstraction cannot reach (quantitative comparison
in \S\ref{sec:related}).
